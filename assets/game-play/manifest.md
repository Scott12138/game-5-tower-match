## 四、定稿工艺（本轮踩到的坑，务必照做）

1. **★ 子容器坐标系绝不能混用**（第 15 轮抓到）：「安全区 682×682」是按**屏幕坐标**描述的（屏 y 326–1008），而牌堆容器 `#pile` 的坐标原点在**桌面左上角**（屏幕 y 292）。把屏幕 y 直接喂给容器 → **整堆牌下移 292px，压到底带 HUD 上**。截图上"看着还行"（牌还在桌面上、只是偏下），只能靠 `pileBox()` 几何断言拿到 `y -178 ~ 927` 才暴露。
   - 修法：容器内一律用**相对坐标** `const SAFE = { x:34, y:326 - 292, w:682, h:682 }`，并在常量旁写注释说明"此处减 292 的原因"。
   - 通用规矩：**凡"某区域（屏幕坐标）内放一个子容器"的计算，先问清这个容器自己的原点在哪**；减完要**断言一遍边界**，别靠看图。
2. **★ "浮在条上方"的文字会撞相邻控件**（第 15 轮抓到）：`.progTxt` 原用 `top:-6px; transform:translateY(-100%)` 浮在进度条上方，与暂停按钮（y 96–184）**垂直 + 水平双向重叠** —— 两段文字叠在一起，截图上看只是"字有点挤"。
   - 修法：改为**条内嵌字**（`.progWrap` 230×28，`.progTxt` 条内 `left:14px` 垂直居中），并补 `G0a~G0e` 5 项不重叠断言。
   - 通用规矩：**用负偏移 / 位移把元素"挪到另一个元素的地盘"时，必须按"挪完之后的矩形"重算碰撞**，不能按原位算。
3. **★ 测量函数必须排除 `display:none` 元素**（第 15 轮抓到）：`pileBox()` 遍历 `.tile` 求包围盒，但**已飞入槽位的牌**还留在 DOM 里且 `display:none` → `getBoundingClientRect()` 全 0，换算成容器相对坐标后变成大负数（`-120`），造成**假失败**。
   - 修法：`if (r.width < 1 || r.height < 1) return;`，并额外输出 `measured` 计数（实测 36 / 36）自证"跳过的确实是隐藏元素，不是漏测"。
   - 通用规矩：**"测量工具本身"也要带自证字段**（测了几个、跳了几个），否则分不清"没量到"和"本来就没有"。
4. **★ 判据要写"状态真的变了"，不是"元素存在"**（沿用第 14 轮纪律）：本轮用无头 Chrome + CDP 派发**真实鼠标事件**（`mouseMoved / mousePressed / mouseReleased`）验证"点牌 → 槽位 +1"（`0 → 1`，并读源牌是否已从牌堆收起），而不是靠截图或自动演示。
   - 反面教材（历史）：只截了图 + 让 `autoPlay()` 直接调函数跑通一局，**恰好绕过了事件层**，交付后才发现连点都点不动。
5. **★ 遮挡判定的"元素集合"必须随 UI 增删同步更新**（第 16 轮抓到，**上一轮遗留缺陷**）：复活徽标原挂在槽位条右侧（`right:36; top:14` → x 507.6–714 / y 1056–1140），与槽位条**同一行同高**，实测**压住第 6、7、8 三个槽位**。
   - 为何上一轮没发现：第 15 轮的命中测试只遍历了 `.hudBottom .item` 与顶带按钮（`.pause / .ruleBtn`），**没把复活徽标放进被检集合**；而它 `display:none` 时又量不到，于是"新加了一个浮层"这件事在断言里完全不可见。
   - 修法：移到顶带空档（x 344–515.5，与暂停/关卡同高），并补 **3 条回归断言**（`reviveHitsSlots` 必须为空 / 不侵 capsule / 落在顶带内）。
   - 通用规矩：**每新增一个浮层 / 徽标 / HUD 元素，同步扩"命中测试与重叠检查"的元素清单**；否则遮挡类缺陷永远测不出来（截图里"看得见"不等于"测得到"）。
6. **★ 无头 Chrome 里"偶发失败"要先怀疑过渡动画的采样时刻**（第 16 轮）：`G1 审查叠加可开` 曾用 `getComputedStyle().opacity === '1'` 判定，而该层有 `.18s` 过渡 —— 等 220ms 通常在过渡结束后，但偶发仍会采到插值中间值（`0.98`）而假失败。
   - 修法：判据改成 `parseFloat(opacity) > 0.95`；同理"等 N 秒后应到账"的等待从 5.7s 放宽到 6.3s。
   - 通用规矩：**凡断言"过渡 / 计时结束后"的状态，判据用阈值而非等于，等待留足余量**；出现偶发失败要复跑定位，不能当没发生。
   - 附：同一轮里同类判据要**统一收口**（本轮把 4 处"等于"改成阈值 / 放宽等待），否则会反复出现"3 次绿 1 次红"。
7. **★ 归档到子目录后，页内资源引用要整体降一级**（第 17 轮）：定稿产物落在 `assets/game-play/`，而工作稿在工作区根目录、页内写的是 `./assets/xxx` —— 归档后必须整体改为 `../xxx`（相对根目录降一级；`assets/_src/...` 同理）。
   - 判据**不能只看脚本打印的"残留 0 处"**（那只是文本层面）——还要**真实打开归档页**断言：所有 `<img>` 无 broken（`naturalWidth === 0`）且相对引用逐个加载成功。
   - 通用规矩：**归档 = 位置变了，相对路径就得跟着变**；凡"搬运自包含页面"的动作，都把"路径重写 + 加载自检"并作一步做完。
   - 附：本轮经验 —— 裸 `assets/`（不带 `./` 前缀）出现在页面**说明文字**里是正常的，不应被重写；重写只针对 `./assets/` 引用前缀，完成后按 `src/href` 正则查残留即可。

**★★ 本轮修正的两条测量判据（延续 5.1b 的"判据本身也要被验证"口径）**

1. **"水印探测"不能用暗像素判** —— 本想"探测到才抹、不无条件抹"，用 `右下角最小亮度 < 阈值` 判，结果把**五万 v1 的深绿毛毡暗部（V=19）误判成水印**。**深色内容 ≠ 水印。** → 改回**无条件裁除底部水印带（y ≥ 1425，与第 17 轮同工艺）**，并把该行判据换成**背景纯度检查**。
2. **主体定位会被"有色背景"污染** —— 五万 v1 的绿毛毡饱和度很高，**被算进了主体**，bbox 高度虚增、牌体宽高比量成 0.609。**测量结果先于肉眼暴露了缺陷。** → 新增自检：**四角各取 80×80 块，S 通道最大值 > 60 即判"背景带彩度"**，此时 bbox 不可信。
3. **指标与视觉打架时以视觉为准，并写清指标为何失真** —— 六萬 红覆盖率 **0.045**（同批中位 0.100，看似"笔画太细"）；放大目视后确认笔画是**厚实高浮雕**，是**指标把深红阴影（V 低于 105 下限）排除了**。→ 判定合格，但在交付说明里写清失真原因，**既不误杀也不默默放过**。

**★ 本轮新增的三条硬教训（都已写进 `tile_prompt.py` 的源码注释）**

1. **★★ 同批生图必须"串行单发"** —— 首次把六筒 + 九条**并行**投喂，**同秒撞名互相覆盖，两张只活下来一张**（ImageGen 落盘文件名 = 提示词首段 + 时间戳，同秒即同名）。**并行 = 白烧一次 token。**
2. **★★ "精确数量"必须逐项点名否定，且模型仍会反复画错** —— 六筒依次出成 **8 枚 → 9 枚 → 6 枚**（v1 全绿单色 / v2 八枚误排 / v3 九枚无金框 / v4 达标），九条依次出成 **12 根 → 9 根无金框 → 背景混毛毡 → 18 根**。**"EXACTLY N / 2×3 / 3×3" 这类计数指令对模型极不稳**，护栏要写成 `Do NOT draw nine, do NOT draw a 3 by 3 block, do NOT draw eight, do NOT draw four`（**把错误数量逐一点名**）才略有效。
3. **★★ 图案计数不做机器断言 —— 投影法 / 连通域法都会被牌面纹路击穿** —— 实测：九条 v2 用"深绿像素行/列投影"量出 **7 列 / 21 行**（真值 3 / 3），六筒量出 **3 列 / 4 行**（真值 2 / 3）。原因是**牌体自身的裂纹玉纹 + 竹节的深色节环**都在同一色域内，把投影切成一堆碎簇。**结论：数量一律以目视复核为准**，脚本只报背景纯度 / 主体宽高比这类几何量。（沿用 5.1b「判据本身也要被验证」的口径 —— **一个总是量错的自研判据，比没有判据更危险**。）

|---|---|
| **卡位** | **人工设计、写死**。每张牌位是一组 `(x, y, z)`；**每天换一次**（这才是"每日一关"的含义）。所以它的排列"非常对称、当天固定不变" |
| **发牌** | **真随机洗牌**：先把每种牌**乘以 3** 存进总数组（⇒ **总数必为 3 的倍数，从结构上杜绝"消不完"**），再 `shuffle`，然后按序号填进卡位 |
| **覆盖判定** | 就是**矩形相交**（AABB）。后写入的（渲染在上面）压住先写入的 —— **只要相交就算被压**，没有阈值 |
| **难度结构** | **纺锤形**：上层牌少、中层多、下层少 → 开局宽松、越消越紧 |
| **可解性** | **不保证**。解包分析的一致结论：源码里**没有求解/校验算法**，第二关 28 层，"随机洗牌造成许多关卡本身就是无解的" |
| **能不能保证有解** | 能，而且不难：**逆向构造** —— 准备一摞"3 张一组"的牌，每次取一组放到**当时最高层**的空位上；反序按组消除即为一组解。有槽位时，7 槽里 3 槽要留给"正在凑的那组"、4 槽自由 |

**③ game-5 现状体检（`docs-verify/.../analyze_pile_init.mjs` · 纯 Node 零依赖）**

| 档 | 朝向取值 | 层与层关系 | 发牌张数为 3 的倍数 | **可凑三连精确最大值** | 能否满清 |
|---|---|---|---|---|---|
| 12 | **只有 0°** | 1 层 | **0 / 11 种** | 2 组 = 6/12 张 | **不可**（最多清 50%） |
| 36 | **只有 0°** | 层 = 整体平移 (46,46) | **3 / 20 种** | 8 组 = 24/36 张 | **不可**（最多清 67%） |
| 96 | **只有 0°** | 层 = 整体平移 (34,34) | **10 / 25 种** | 29 组 = 87/96 张 | **不可**（最多清 91%） |

> 可解性用的是**精确解**（非估算）：因「碰」只涉及单一种牌、「吃」只涉及单一花色 ⇒ 问题**按花色分解**，
> 每花色只有 9 个计数 + 7 个「吃」档，穷举「吃」的各档用量即可得全局最大组数。
> **结论：现在这三档牌堆在任何打法下都清不完** —— 这是比"显得假"更硬的缺陷。
